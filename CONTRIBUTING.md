# Contributing to Saffron

Thank you for your interest in contributing to Saffron! This document provides guidelines and instructions for contributing.

## Code of Conduct

This project adheres to the [Contributor Covenant Code of Conduct](CODE_OF_CONDUCT.md). By participating, you are expected to uphold this code. Please report unacceptable behavior to dev@spicelabs.io.

## How to Contribute

### Reporting Bugs

Before creating a bug report, please check existing issues to avoid duplicates. When creating a bug report, include:

- **Clear title** describing the issue
- **Steps to reproduce** the behavior
- **Expected behavior** vs actual behavior
- **Environment details** (Java version, OS, disk image format if relevant)
- **Sample disk image** if the issue is file-specific (ensure it doesn't contain sensitive data)

### Suggesting Features

Feature suggestions are welcome! Please include:

- **Use case** — Why is this feature needed?
- **Proposed solution** — How should it work?
- **Alternatives considered** — What other approaches did you consider?

### Pull Requests

1. **Fork the repository** and create your branch from `main`
2. **Write tests** for any new functionality
3. **Follow the code style** (see below)
4. **Update documentation** if needed
5. **Ensure tests pass** with `mvn test`
6. **Submit the pull request** with a clear description

## Development Setup

### Prerequisites

- Java 21 or higher
- Maven 3.6+
- Git

### Building

```bash
# Clone your fork
git clone https://github.com/YOUR_USERNAME/saffron.git
cd saffron

# Build and run tests
mvn clean install

# Run tests only
mvn test

# Run tests without coverage checks (faster)
mvn test -Pquick

# Generate coverage report
mvn test jacoco:report
# Report is in target/site/jacoco/index.html
```

### Running Specific Tests

```bash
# Run a specific test class
mvn test -Dtest=DiskReaderTest

# Run tests matching a pattern
mvn test -Dtest="*Ext4*"
```

### Corpus Verification Tests

Saffron includes a corpus of 70 real-world VM disk images verified against ground truth generated by external tools (libguestfs running in Docker). These tests are the project's primary correctness guarantee.

**How corpus tests work:**

- Ground truth JSON files live in `src/test/resources/corpus-verification/`
- Each JSON file records filesystem count, file count, directory count, and SHA256 hashes for 20 randomly sampled files per filesystem
- JSON is generated by the Docker scanner in `tools/corpus-scanner/`, **never** from Saffron itself
- Tests use `@EnabledIf("corpusExists")` and are skipped if the `test-corpus/` directory is not present
- In CI, corpus tests are skipped (disk images are too large to store in the repository)

**To run corpus tests locally:**

1. Obtain the test corpus (ask a maintainer for access)
2. Place images in `test-corpus/` at the project root
3. Run `mvn test` — corpus tests will automatically enable

**Regenerating ground truth** (maintainers only):

```bash
cd tools/corpus-scanner
./run.sh
```

This builds a Docker container with libguestfs, scans all images in `test-corpus/`, and writes JSON files to `src/test/resources/corpus-verification/`.

**Critical invariant:** Ground truth JSON must always come from the external Docker scanner. Never generate JSON from Saffron code. Any variance between Saffron and ground truth is a hard failure — exact filesystem count, exact file count, and correct SHA256 hashes are required.

## Code Style

### General Guidelines

- Use **4 spaces** for indentation (no tabs)
- Maximum line length: **120 characters**
- Use **meaningful names** for variables, methods, and classes
- Write **self-documenting code**; add comments only when necessary
- Follow **Java naming conventions**

### Null Safety

This project enforces a strict no-null policy:

- Use `@NotNull` annotation on all parameters that must not be null
- Use `Optional<T>` for return values that may be absent
- Never return `null` from any method

```java
// Good
public @NotNull Optional<String> label() {
    return Optional.ofNullable(volumeLabel);
}

// Bad
public String label() {
    return volumeLabel; // Could return null!
}
```

### Immutability

- Prefer immutable objects (records, final fields)
- Use `List.copyOf()` and `Map.copyOf()` for defensive copies
- Don't expose mutable internal state

```java
// Good
public record FilesystemInfo(
    @NotNull FileSystemType type,
    @NotNull Optional<String> label,
    @NotNull Optional<String> uuid
) {}
```

### Sealed Interfaces

Saffron uses sealed interfaces extensively for type safety:

```java
// VirtualDisk, FileSystem, FileSystemEntry, PartitionTable, Partition
// are all sealed interfaces — use pattern matching in switch expressions

String info = switch (entry) {
    case FileSystemEntry.RegularFile f -> "File: " + f.basicInfo().size();
    case FileSystemEntry.Directory d -> "Dir: " + d.basicInfo().name();
    case FileSystemEntry.SymbolicLink l -> "Link -> " + l.target();
    case FileSystemEntry.SpecialFile s -> "Special: " + s.basicInfo().name();
};
```

### Error Handling

- Use `SaffronException` and its subclasses for Saffron-specific errors
- Include helpful error messages with context
- Don't catch generic `Exception` unless re-throwing

```java
// Good
throw new InvalidMagicException(
    String.format("Expected QCOW2 magic 0x%08X, got 0x%08X", EXPECTED, actual));

// Bad
throw new RuntimeException("Bad magic");
```

### Testing

- Write unit tests for all new functionality
- Use descriptive test method names
- Test edge cases and error conditions
- Aim for 80%+ code coverage (enforced by JaCoCo)

```java
@Test
void open_withValidQcow2_returnsQcow2Disk() throws Exception {
    try (VirtualDisk disk = DiskReader.open(testImage)) {
        assertThat(disk.format()).isEqualTo(DiskFormat.QCOW2);
        assertThat(disk.virtualSize()).isGreaterThan(0);
    }
}

@Test
void open_withCorruptedFile_throwsInvalidMagicException() {
    assertThatThrownBy(() -> DiskReader.open(corruptedPath))
        .isInstanceOf(InvalidMagicException.class);
}
```

## Commit Messages

Follow the [Conventional Commits](https://www.conventionalcommits.org/) specification:

```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

Types:
- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation only
- `style`: Code style (formatting, no code change)
- `refactor`: Code change that neither fixes a bug nor adds a feature
- `test`: Adding or correcting tests
- `chore`: Maintenance tasks

Scopes:
- `disk`: Disk format support (qcow2, vmdk, vhd, etc.)
- `fs`: Filesystem support (ext4, ntfs, xfs, etc.)
- `partition`: Partition table handling
- `lvm`: Logical volume manager support
- `security`: SecurityPolicy and related
- `api`: Public API changes
- `corpus`: Corpus verification infrastructure

Examples:
```
feat(fs): add exFAT filesystem support

fix(disk): handle unsigned grain table entries in VMDK

test(corpus): add Fedora 39 disk image to corpus

docs: update README with LVM usage example
```

## Release Process

Releases are managed by maintainers. The process is:

1. Update version in `pom.xml`
2. Create a GitHub release with a `vX.Y.Z` tag
3. CI automatically builds, signs, and publishes to GitHub Packages and Maven Central
